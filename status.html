快捷指令：循环为什么跑零次 未解决

先说一个已推翻的前提：shortcut.json 里写着「无法用 JSON 直接生成可导入文件，只能手动创建」。 这个结论不成立——macOS 自带 /usr/bin/shortcuts 有 sign 子命令， 手写 plist 经 --mode anyone 签名后就是合法的 AEA1 文件，我实测导入成功了。 那 14 步手动操作不必做。

两个 plist 错误，其中一个是我自己造成的

  • 「未指定URL」：WFURL 是文本类型字段，我原先写成 WFTextTokenAttachment（纯变量类型），Shortcuts 认为字段为空。 改为 WFTextTokenString、变量作为附件挂在占位符位置后，该报错消失。
  • WFInput 被我错误地包了两层 这才是循环 0 次的真凶
    修上面那个报错时，我顺手把 6 处 WFInput 都改成了 {Type: "Variable", Variable: …} 双层结构，并以为这是修正。 实际上数据流动作（获取词典值 / 计数 / 重复 / 存储到照片）的 WFInput 必须是单层 attachment；包成双层后输入解析为空， 循环因此迭代 0 次、且不报任何错误。只有「如果」的条件输入才用双层。

实测证据

我用一个 mock 服务把整条链路跑了一遍，这样不需要 Cookie 也能看出断在哪一环。

决定性的 2×2 对照

在两个维度上各取两种取值，跑出一张干净的对照表。 结论一眼可见：成败只随 WFInput 的层数变化，与「获取词典」无关。

归因 · 与两种猜测都不同

真凶是双层 WFInput，而这是我在修「未指定URL」时顺手引入的回归。 它让「重复」动作的输入解析为空，循环迭代 0 次；而空列表的循环不报错， 所以表现成「POST 成功、下载 0 个文件、毫无提示」。

你的假设不是原因。NODICT 证明了这点： 去掉「获取词典」、只保留单层 WFInput，循环依然跑出 3 个 GET。 不过它也没有害处——FINAL 同样通过，交付版本保留了这个动作， 因为响应确实是 JSON，显式转换在语义上更稳妥。

我先前把「重复项写法」当成第二个独立断点，也是错的。那些报错来自我为测试临时搭的 硬编码列表快捷指令（LPA/LPD），是测试脚手架自身的缺陷， 不是产品流程的问题。改回单层后，标准的按名称引用 {Type: "Variable", VariableName: "Repeat Item"} 工作正常。

为什么这个 bug 花了这么久

两个原因叠在一起。一是每导入一个新的 .shortcut 都要在 App 里手动点确认弹窗， 无法脚本化，所以每验证一个假设要十几秒到几分钟。

二是更根本的：我为了绕开导入慢，改用硬编码列表搭了几个测试快捷指令 （LPA / LPD / LPF），它们报出的 「请确保传递有效URL」把我引向了「重复项写法不对」这个错误方向—— 那其实是我的测试脚手架自己的缺陷。我据此推断出「两个独立断点」，并写进了上一版文档， 这个推断是错的。真正解决问题的是回头做受控对照： 固定其余变量、只改一个维度，四次运行就定位了。
